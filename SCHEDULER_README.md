# Continuum Workflow Scheduler Optimizer

`scheduler_optimizer.py` is a Python-based orchestrator script designed to sit on top of the NFR Continuum Simulator. It dynamically explores the massive search space of deployment combinations across the Edge-Fog-Cloud continuum, testing different topological placements and Non-Functional Requirement (NFR) configurations to find the optimal deployment that minimizes overall Makespan ($C_{max}$) while adhering to strict energy budgets.

## Core Concepts

The script operates in an **iterative optimization loop**:
1. **Candidate Generation**: Maps every workflow task (e.g., preprocessing, inference, archiving) to every physical tier in the continuum (Edge, Fog, Cloud) and tests various NFR combinations (e.g., LZ4 vs BZ2 compression, AES vs CHACHA20 encryption).
2. **Dynamic Configuration Generation**: For each candidate, it auto-generates a valid `config.json` that the C-based simulator natively understands.
3. **Oracle Execution**: Programmatically invokes the C simulator (`proxy_dd/main`) via subprocess, evaluating the real-world execution times and power consumptions.
4. **Metrics Extraction & Selection**: Reads the output profiling data (`energy_by_machine.csv` and `stage_totals_by_workers.csv`) generated by the simulator, discarding candidates that exceed predefined energy limits, and selects the remaining viable configuration with the absolute lowest makespan.

## Prerequisites
- Python 3.x
- The compiled NFR simulator executable (typically `proxy_dd/main` or `./simulator`).
- Valid simulator traces and power models configured in your workspace.

## Usage

You can run the script from the root of the simulator project. By default, it requires you to specify the path to the simulator executable.

### Basic Command
```bash
python3 scheduler_optimizer.py --simulator-cmd proxy_dd/main --simulator-dir proxy_dd
```

### Command-Line Arguments

- `--simulator-cmd`: **(Required)** The path to the simulator executable (e.g., `proxy_dd/main`).
- `--simulator-dir`: Directory where the simulator operates and drops its `results/` folder (default: `.`).
- `--global-budget`: The maximum allowed energy consumption for the entire continuum pipeline in Joules (default: `500000.0`).
- `--edge-budget`: The strict maximum allowed energy consumption specifically for the Edge node in Joules, representing battery capacity constraints (default: `8000.0`).

### Example with Constraints

```bash
python3 scheduler_optimizer.py \
    --simulator-cmd proxy_dd/main \
    --simulator-dir proxy_dd \
    --global-budget 1500000.0 \
    --edge-budget 8000.0
```

## How It Works Under the Hood

1. **Semantic Task Names**: In the script, you define tasks using human-readable semantic names (`preprocessing`, `inference`, `archiving`). 
2. **C Simulator Compliance**: When generating the `config.json` files for the C simulator, the script silently re-maps these to the strict identifier format the C parser requires (`stage1`, `stage2`, `stage3`).
3. **Execution Context**: The script carefully resolves the simulator binary to an absolute path and passes `cwd=simulator_dir` into the `subprocess.run` loop. This guarantees that the simulator spawns correctly, locates its required trace generators relative to its working directory, and outputs the `results/` metrics into the expected folder.
4. **Metric Harvesting**: It scans `results/energy_by_machine.csv` and `results/stage_totals_by_workers.csv` to capture the `Edge Energy`, `Total Energy`, and `C_max`.

## Customizing the Search Space

To test new topologies or NFR algorithms, simply edit the arrays at the top of the `main()` function inside `scheduler_optimizer.py`:

```python
tasks = [
    {"name": "stage1", "desc": "preprocessing", "service_time": 1.2, "requires_nfr": True, "b_fs": 100},
    # ...
]

machines = [
    {"name": "Edge", "max_power": 8.0, "static_power_percent": 0.35, "power_model": "linear", "hardware_profile": "pi5"},
    # ...
]

nfr_options = [
    {"compression": "LZ4", "encryption": "AES"},
    # ...
]
```
